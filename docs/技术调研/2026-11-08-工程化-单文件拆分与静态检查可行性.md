## 0. 一页结论（给调度）

1. **先别拆。** 真正卡住团队的不是“文件大”，而是**没有静态检查**和**按组的测试总是一起跑**。这两件事都能在单文件里做完、不碰任何产品行为，性价比远高于拆文件。
2. **拆的第一个候选是“纯 UI 展示块”约 15 万字节（占 index.html 25.2%、占界面脚本 50.3%）**：头像 / 教练文案 / 音乐 / 训练（复盘·牌效·防守·看板）/ 规则设置 / 主界面。它们**不碰引擎、不被服务端加载**，抽走后 `rooms.js`、`core.test.js` 一行都不用改。
3. **最不该拆的是引擎**（`index.html:1002–2911`，95,968 B）。`server/rooms.js:22-27` 与 `tests/core.test.js:8-12`、`multi.test.js:13-14`、`draw-nth.test.js:21-22`、`evaluation/run-risk.js:46` 全都按“**取第一个 `<script>` 块**”读它；动它等于同时改服务端权威引擎与五个消费方，收益为零、风险最高。
4. **不建议动**：引入构建管线（esbuild/Closure）、`<script type="module">`、把 game.js 拆成几十个小模块、重写联机层。

| 消费方 | 位置 | 怎么读引擎 | 拆文件会不会坏 |
| --- | --- | --- | --- |
| 服务端权威牌局 | `server/rooms.js:22-27` | `readFileSync(index.html)` → `/‹script\b[^>]*›([\s\S]*?)‹\/script›/` 取**第一个** script → `new Function(...)` 执行 → 要求长度 ≥ 20000 | **会**。引擎挪出 index.html 就没得读 |
| 单元测试 3 处 | `tests/core.test.js:8-12`、`multi.test.js:13-14`、`draw-nth.test.js:21-22` | `html.indexOf('(function (root, factory) {')` → 到 `</script>` 切片 → `vm.runInNewContext` | **会**（同上） |
| 浏览器门禁 | `tests/pages-compat.js:65`、`browser-online.js:67` | 起本地 HTTP，从 `index.html` 读页面 | 页面级，**不坏**（但要多放行一个静态文件） |

## 3. 三条“现在就落后”的判断（带位置）

### 落后 1｜没有静态检查，`node --check` 也不在门禁里

- **现状**：`tests/run-checks.js:121-147` 的 job 清单里，只有 `--test`（跑测试）与服务端脚本，**没有任何一个 job 对 `index.html` 或 `server/*.js` 做语法/类型检查**。引擎与界面脚本的语法错误，只会在浏览器跑起来时才暴露。
- **代价实例**：本轮做探针时，本鱼第一次切引擎块切错两行，`node --check` 立刻报 `SyntaxError: Unexpected token '<'` —— 这种“切片契约”本身靠人记，一旦 `index.html` 结构漂移，`server/rooms.js:23` 取到的是 `no-build-check.js` 校验之外的错误块，要到联机开局才炸。
- **参照**：`node --check`（Node 官方 CLI，`-c, --check`）；`tsc --checkJs`（本机 1.6 s / 10 行，见 §2）。
- **成本/收益**：成本 ≈ 1 小时（写一个 `tests/syntax-check.js`，遍历 `repo/**/*.js` + 切片后的引擎块，`node --check` 逐个跑）；收益：把“改完页面一开就白屏”这类错误从浏览器前移到 Node 门禁。

### 落后 2｜代码风格其实**已经统一**，缺的是“守风格/守签名”的机械规则（结论与直觉相反，特此写清）

- **实测计数（不是印象）**：`index.html:2913-7799` 里**所有** 229 个顶层函数都用 `function` 声明（行首 `  function `），`const X = (...) =>` 形式 **0 处**；2 空格缩进一致。**所以“风格乱”不是本项目的病**，不需要格式化工具。
- **真正的缺口是签名位错位这类 bug**：本项目已经有实例——A 方案的 `manualDraw` 必须区分“正式对局”与“测试/脚本构造的局”，这类区分靠的是构造参数而不是函数里某个字段；一旦有人给某个函数多传/错传一个参数，**语法检查、现有 19 个 Node 测试都不会响**。
- **参照**：ESLint `no-unused-vars` 默认 `args: "after-used"`，第 1 个参数未用但第 2 个用了就**不报**；要抓“参数位错位”必须显式配 `args: "all"`（官方文档核实，见 §2）。这正是本项目该配的那一档。
- **不建议**：引入 Prettier 全量重排——风格本来就一致，重排只会把 `tests/audio.test.js:138/141` 这类**逐字锁代码**的断言打红，收益为零。

### 落后 3｜测试按“页面”分，不按“功能域”分，改一处必须全量 31 组

- **现状**：`tests/run-checks.js:126-146` 把 24 组浏览器页 + 1 组 online 平铺；每轮改动都要 `node tests/run-checks.js --browser` 跑全量（v54 实测 164.3 s；`table-3d-ui` 一组就占 38–42 s）。
- **代价**：单跑绿 ≠ 全量绿（PROJECT_MEMORY 的行动指南已写明），所以每次小改都要付全量成本；而 `table-3d-ui` 在满载下偶发超时（`:71-77` 2000 步性能断言、掷骰竞态），把“全量绿”本身变成一个噪声源。
- **参照**：Node 内置测试的 `--test-shard` / `--test-name-pattern`（[Node test runner](https://nodejs.org/api/test.html)）可以把 Node 侧 19 个测试文件分片；浏览器侧可以在 `run-checks.js` 里加 `--only=<组名>`，同时保留全量入口。
- **成本/收益**：成本 ≈ 半天，且**不碰任何断言**（只加筛选参数）；收益：日常小改从 164 s 降到 10–40 s；`table-3d-ui` 这类长尾只在新版首次全量时跑。

## 4. 拆分方案对比（若确要拆）

### 方案 A：拆纯 UI 区（推荐，但**排在落后 1/3 之后**）

```
index.html          仍然一张页面、自包含、无外链 → no-build-check 不红
 ├ 内联 #1：引擎（原样不动，rooms.js/core.test 等 5 处消费者零改动）
 ├ 内联 #2：game.js 核心（主循环/渲染/手牌/拖拽/联机/账号）
 └ 内联 #3：game-ui.js = 头像 + 教练 + 音乐 + 训练四页 + 规则设置 + 主界面（约 151 KB）
```
- **必须先改的前置**：`tests/atmosphere.test.js:307-308` 断言了 `'<script id="mahjongCore">'` 存在**且在最前**——这条不变；其余 UI 相关断言（教练/头像/音乐/训练）多数在 `.html` 页面里按 DOM 断言，**不按 script 块序号**，所以不拦。
- **怎么做到“抽走不漏”**：UI 块的函数现在都读闭包里的 `cfg`，所以拆分方式是“新建一个 IIFE，把 `cfg` 读写入口显式传进去”，**函数体整段照搬、不重写**——断言逐字不变。
- **风险**：`window.onerror` 报错行号会因文件变段而改变（`:2915` 那段把行列数写进提示文案），排障时会多一层心理成本；`renderSeat → insertSeatAvatar` 这种调用要显式挂到命名空间上。
- **收益量级**：人读 `game.js` 从 4,887 行降到约 3,600 行；单次 review 需要看的代码减少一半。

### 方案 B：把引擎挪成 `core.js` 外链文件（**不建议**）
- 会让 `server/rooms.js`、`core.test.js`、`multi.test.js`、`draw-nth.test.js`、`run-risk.js` 五个消费者同时改；`no-build-check.js:22-25` 的“所有 script 必须内联”当场红。
- 会让“离线可用 + GitHub Pages 直接能跑”多一个请求，`sw.js` 也要加资源。
- **唯一能直接受益的场景**是“服务端不再靠正则切 HTML”——这件事可以**不改产品**地做到：给 `rooms.js` 加一条“若存在 `core.js` 则优先读它”的兼容分支，但本鱼**不建议**为假设中的收益改服务端。

### 方案 C：上构建（esbuild 出单文件）
- 与 `no-build-check.js`、路线文档“单文件、零外链、零构建约束不变”**直接冲突**；`package.json` 出现即被 `no-build-check.js:32` 判红。
- 除非用户明确愿意放弃“零构建”，否则**不做**。

## 5. 不建议动（避免过度工程）

1. **引擎块结构**：`<script id="mahjongCore">` 的 UMD 包装、`(function (root, factory) {` 开头、导出对象位置——5 处消费者按字面找它。
2. **`sw.js ASSETS` 与版本链四处**：拆文件必然多一项缓存资源，版本链从 4 处变 5+ 处，出错面翻倍。
3. **`tests/audio.test.js:138/141` 这类“逐字锁代码”的断言**：不要为它们的红/绿去重构产品代码。
4. **联机层（`index.html:6997–7634`）与代理牌局**：现在是服务端权威 + 客户端只画，拆它属于协议级重构，不是工程化整理。
5. **全量 Prettier/ESLint 自动改档**：会把现有 19 个 Node 断言里的字面串改到红。
