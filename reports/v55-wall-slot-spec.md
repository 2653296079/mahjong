# v55 阶段一 1a：三维牌墙槽位定义（交付文档，零产品代码改动）

落笔：三维。本文件**只描述现有代码的槽位契约**，不含任何产品代码改动，供码仔在二维侧计算 `wallSlotMap` 使用。
依据：`assets\table3d\table3d.js` 的 `physicalWall()`（388-400）与 `wallRemainder()`（401-406），**读的是无 BOM 的 HEAD 版 `AA463679…`**。

## 1. 槽空间总览

- **槽总数 108，即 54 墩**，不是 136。三维牌墙只铺**未发牌的部分**，已发走的 52 张不在墙上。
- 槽号 `0..107`，**0 是起点，107 是终点**。码仔此前写的 `0..101` 作废。
- 四家按 `[0, 3, 2, 1]` 顺序铺，**每家的墩数取决于 `seat % 2`**：`seat` 为 0、2 时 **14 墩（28 槽）**；`seat` 为 1、3 时 **13 墩（26 槽）**。
- 累加得到四家的槽基准偏移：

| 顺序 | seat | 墩数 | 槽数 | 基准偏移 | 槽区间 |
|---|---|---|---|---|---|
| 1 | 0 | 14 | 28 | **0** | 0–27 |
| 2 | 3 | 13 | 26 | **28** | 28–53 |
| 3 | 2 | 14 | 28 | **54** | 54–81 |
| 4 | 1 | 13 | 26 | **82** | 82–107 |

累加校验：`28 + 26 + 28 + 26 = 108` ✔

> **更正**：三维此前在群里口头说过"家偏移 0 / 28 / 54 / 80"，**那个 80 是错的**，正确值是 **0 / 28 / 54 / 82**。原因：第 4 家的偏移 = 前三家槽数之和 = `28 + 26 + 28 = 82`，不是 80。**码仔请以本表为准。**

## 2. 每家内部：列与层

```js
for (let column = 0; column < count; column++) for (let layer = 0; layer < 2; layer++)
```

- **先列后层**：外循环 `column`，内循环 `layer`。所以同一墩的两个槽**连续**：`列 c` 的上层是 `基准 + c*2`，下层是 `基准 + c*2 + 1`。
- **`column` 从右向左数墩**（代码注释原话："每家从右向左数墩；每墩先上后下"）。
- **上层在前**：`layer = 0` 是上层（`y = TOP + 0.018`），`layer = 1` 是下层（`y = TOP`）。
- 列坐标：`x = ((count - 1) / 2 - column) * 0.027`，横向量随 `column` 增大而减少。
- 与座位的关系：`pos = (seat + seatOffset) % 4`，**这是玩家视角的相对方位，不是绝对座位号**。二维若按绝对 seat 推方位，必须自己套这层 `seatOffset`。

## 3. `startSlot` 旋转（关键：二维不许再转）

```js
const start = opening?.startSlot || 0;
return result.slice(start).concat(result.slice(0, start));
```

`physicalWall()` **已经把数组按 `startSlot` 旋转过了**。也就是说 `physicalWall()[i]` 对应的是"原始槽 `(i + startSlot) % 108`"的位置。

**所以二维计算 `wallSlotMap` 时，拿到的 `wall[i]` 已经是旋转后的顺序，绝对不能再自己转一次 `startSlot`，否则就是双旋，整桌牌错位。**

## 4. `102..107` 这 6 个槽是什么

`wallRemainder()`：

```js
const head = draws ? draws.head : 102 - Math.max(0, next.wallCount || 0);
const tail = draws ? draws.tail : 0;
return wall.slice(head, 102 - tail).concat(next.over ? [] : wall.slice(102));
```

回答码仔的问题：**`102..107` 不是"另外 3 墩"，也不是"补位"**——它是 `physicalWall()` 按四家顺序铺满 108 槽后**本来就存在的最后 6 个槽位**（落在第 4 家、即 `seat = 1` 的尾部），只是被发牌规划当作**尾部鸟牌区**使用：

- 牌局进行中（`next.over` 为假）：`slice(102)` 的 6 个槽**照常渲染**，拼在 `slice(head, 102 - tail)` 后面；
- 牌局结束（`next.over` 为真）：`slice(102)` 的部分**整体丢弃**，返回空数组。

## 5. 两套坐标系必须靠对照测试锁死

| 坐标系 | 来源 | 起点含义 |
|---|---|---|
| 二维墙下标 | `hand.wall` 的 `i`，`drawFor` 用 `shift`/`pop` 取 | `i` 是"发牌后重排的下标" |
| 三维可视槽 | `physicalWall()` 的槽号 `0..107` | 已含 `startSlot` 旋转 |
| 三维剩余区段 | `wallRemainder()` 的 `slice(head, 102 - tail)` | `head=wallDraws.head`（开局为 **52**），`tail=wallDraws.tail` |

**`head` 初值 52 是 `wallDraws.head` 的初值，而 `102` 是三维墙的固定边界**——两个数字不同源，**不能互相当作同一套坐标**。这就是为什么必须有对照测试。

## 6. 对照断言（供码仔写测试，三维不代写）

给定 seed 与 `opening`：

**基础算式（先算清，再写断言）**

```
deck 总槽 108 → 发走 52（openingPackets）→ deck[52] 留作首摸
wall = [deck[52]] + deck[53..107] → 1 + 55 = 56 张
再切鸟牌 6 张（RULES.birdCount = 6）→ wall.length = 50
H.wall[0]   → deck 52
H.wall[i]   → deck 52 + i        (i = 1..49 时也应满足 52+i)
H.wall[49]  → deck 101
```

**断言**

1. 头部方向：无杠补时，`H.wall[i]` 的可视槽位 == `52 + i`（i = 0..`H.wall.length-1`）；
2. 尾部方向：`pop()` **取走之前**，那张的可视槽位 == `101 - tail`；
3. **恒等式校验（唯一正确的写法）**：`head + H.wall.length + tail === 102`。
   它天然同时覆盖头摸与尾补：头一摸 `head` 增 1、`len` 减 1；尾一补 `tail` 增 1、`len` 减 1；两边永远守恒。
   不相等说明有别的路径改动了墙。
4. 项数守恒：`wallRemainder()` 项数 == `wall.slice(head, 102 - tail).length + (over ? 0 : 6)`；
5. 旋转校验：第 `head` 个可视槽对应的原始槽 == `(head + startSlot) % 108`；
6. `over` 为真时，`slice(102)` 的 6 项必须缺席。

> **更正（三维两次写错，以此节为准）**
> - 原第 3 条写作 `102 - tail - 1`：**错**。`102` 是鸟牌区起点，不是墙尾最后一张；墙最后一张在 `101`。
> - 第二版写作 `52 + H.wall.length - 1 ≡ 101 - tail`：**错**。该式只在 `tail` 变化、`head` 不变时成立；一旦头摸，`head` 增 1、`len` 减 1，左边掉 1 而右边不动，立刻失效。
> - **正确恒等式只有 `head + H.wall.length + tail === 102`**；单张槽位分开写：下一个头摸 = `head`，下一个尾补 = `101 - tail`。

**跨家边界断言（Chief 硬要求，只在首尾取样测不出偏移错）**

7. 槽位 **27 / 28**、**53 / 54**、**81 / 82** 三对边界，各自左右两个槽必须落在正确的家与列层上（按 §1 的 `0 / 28 / 54 / 82` 偏移）；
8. `map[0]` 落跳牌位 **52**、`map[len-1]` 落槽 **101**（鸟牌切走前最后一张，不是 107）。

> 只在首尾取样时，错误的 `80` 与正确的 `82` 都能通过；**必须靠第 7 条才可区分。**

## 7. 边界提醒（防作弊，不可越）

- **槽位号可反查，牌种不可反查**。跨显示边界的只有：自己手牌、公开副露、牌河、对手张数，加纯数字的 `wallCount` / `wallDraws`。
- 牌墙一律渲染为牌背；`102..107` 同样只能渲染牌背。
- 三维侧**不实现** `startSlot` 旋转 / 发牌位图 / 跳牌位 / 鸟牌切割的换算，那套逻辑只在二维一处。

## 8. 1b 只读接口设计（仅文档，未写代码）

> 本节是设计稿。**调度令：验牌跑全量期间不许改任何会被跑到的文件**，所以本节只写不实现，等门禁跑完再落地。

### 8.1 原则

- **零渲染改动**：牌背已是 `InstancedMesh`（`table3d.js:221`，上限 160，`setMatrixAt(i)` 逐张写矩阵），"可指认"这层已经具备，**不需要拆成逐牌实体**；
- **纯查询**：新增接口只读计算，不改 `entries` / `snapshot` / 渲染状态，不触发 `schedule()`；
- **不传牌种**：返回结构里只有数字槽位与方位，绝不含 `kind`。

### 8.2 挂接点

`table3d.js` 的返回对象（`return { ... }`，804-831），与 `tileDragTarget()` 并列，写法参照它：

```js
wallSlotAt(index) {                    // index = 可视槽下标 0..107
  const opening = snapshot?.opening;
  return wallSlotInfo(index, opening); // 返回 { physical, seat, pos, column, layer, upper }
},
wallSlotCount() { return WALL_SLOTS; } // 108
```

### 8.3 返回字段语义

| 字段 | 含义 |
|---|---|
| `physical` | 旋转后的物理槽号（0..107） |
| `seat` | 绝对座位号（0/1/2/3），按 `[0,3,2,1]` 铺序反查得到 |
| `pos` | 玩家视角的相对方位 `(seat + seatOffset) % 4` |
| `column` | 该家内从右向左的第几墩（0 起） |
| `layer` | 0 = 上层（`y = TOP + 0.018`），1 = 下层（`y = TOP`） |
| `upper` | `layer === 0` 的布尔便捷值 |

### 8.4 边界断言（归三维侧验证）

码仔的 `wallSlotMap` 值域只有 52..101，**到不了四家边界**，所以这几条必须由三维侧断言：

1. 槽 **27** 属于 `seat=0` 的 `column=13 / layer=1`；槽 **28** 属于 `seat=3` 的 `column=0 / layer=0`；
2. 槽 **53** 属于 `seat=3` 的 `column=12 / layer=1`；槽 **54** 属于 `seat=2` 的 `column=0 / layer=0`；
3. 槽 **81** 属于 `seat=2` 的 `column=13 / layer=1`；槽 **82** 属于 `seat=1` 的 `column=0 / layer=0`；
4. 这些断言必须**成对**存在——只测首尾（0 与 107）时，错误的偏移 `80` 与正确的 `82` 都能通过。

### 8.5 性能

本接口是 O(1) 纯算术（一次取模 + 最多 4 次循环），不在渲染帧内调用，**不改变 `drawCalls`**，因此原定的 `drawCalls` 门槛（+20%/+60%）**一并取消**——不拆实体就没有这项消耗。
